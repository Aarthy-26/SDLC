Issue: Sensitive internal database error details may be exposed to API consumers via `ex.getMostSpecificCause().getMessage()` in repository exception handling.
Severity: High
Recommendation: Log full exception details server-side through SLF4J/Logback and return sanitized application-specific messages to clients.
Compliance Impact: SOC2/internal security policy concern due to information disclosure of schema or database internals.

Issue: Controller, service, repository, DTOs, and SQL constants are all placed in one file, creating a god-file and violating normal Java/Spring layering conventions.
Severity: Medium
Recommendation: Split the implementation into separate files by responsibility: controller, service, repository, request DTOs, and response DTOs. Keep one public top-level type per file.
Compliance Impact: Maintainability and auditability risk.

Issue: Repository methods convert all `DataAccessException` failures into `BadRequestException`, which incorrectly classifies server/database faults as client errors.
Severity: Medium
Recommendation: Use centralized exception mapping so validation errors return 400, missing records return 404, and database/system failures return 500 or 503.
Compliance Impact: Operational correctness and incident triage concern.
