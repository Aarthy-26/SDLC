# Code Review Report — User Story 124442

## Summary
The reviewed file is a **TypeScript React TSX** component for a Sculpt custom component editor and preview flow. It is readable, uses idiomatic React hooks, and addresses likely UI concerns such as modal lifecycle, editor state reset on open, preview refresh, and event-handler preservation. However, from an enterprise security and compliance perspective, the implementation introduces multiple **high-risk client-side execution vulnerabilities**.

The most critical issue is that it executes **user-supplied HTML, CSS, and JavaScript** inside an iframe with an overly permissive sandbox and remote runtime dependencies. In its current form, this is not sufficiently hardened for production use in a regulated or enterprise environment.

## Critical Issues

### 1. Arbitrary untrusted code execution in iframe preview
**Severity:** Critical  
**Location:** `SculptCustomComponent` iframe document write and runtime JS execution

The component writes raw `html`, `css`, and transpiled `js` directly into an iframe document and executes the resulting code. This effectively runs user-authored code without sanitization or policy controls.

**Risk:**
- Malicious scripts can execute in the preview environment.
- The current boundary is not strong enough to consider the execution isolated.
- Users may inject scripts that perform phishing-like UI actions, data harvesting, or abuse of browser capabilities exposed through the sandbox.

**Recommendation:**
- Treat all custom component content as untrusted.
- Sanitize HTML before rendering.
- Disallow inline script execution through HTML content.
- Consider moving preview execution to a safer isolated service or restricted worker-based architecture.
- If JS preview is mandatory, define a constrained execution model rather than evaluating arbitrary user JS.

---

### 2. Overly permissive iframe sandbox
**Severity:** Critical  
**Location:** `sandbox="allow-scripts allow-same-origin allow-modals"`

The iframe sandbox includes `allow-same-origin`, which materially weakens isolation when combined with script execution. `allow-modals` also expands capabilities without clear necessity.

**Risk:**
- Reduced containment of untrusted runtime code.
- Same-origin treatment can enable broader interaction with iframe content and complicate isolation guarantees.

**Recommendation:**
- Remove `allow-same-origin` unless there is a proven and documented requirement.
- Remove `allow-modals` unless specifically required.
- Prefer the smallest possible sandbox, ideally only what is strictly necessary.

---

### 3. Unvalidated `postMessage` trust boundary
**Severity:** High  
**Location:** message event listener in `SculptCustomComponent`

The code accepts any window message where `event.data?.type === "IFRAME_CLICK"` and immediately invokes `onSelectRef.current?.()`.

**Risk:**
- Any other frame or script on the page can post the same message.
- This creates a spoofable event channel and weakens UI trust boundaries.

**Recommendation:**
- Validate `event.source === iframeRef.current?.contentWindow`.
- Validate expected origin where possible.
- Use a stronger message contract with a nonce/session token if this becomes more than a trivial selection event.

Example hardening:
```ts
const handleMessage = (event: MessageEvent): void => {
  if (event.source !== iframeRef.current?.contentWindow) return;
  if (event.data?.type !== "IFRAME_CLICK") return;
  onSelectRef.current?.();
};
```

### 4. Runtime dependency loading from public CDN
**Severity:** High  
**Location:** SWC import from jsDelivr and React import source from esm.sh

The preview bootstraps executable code from public CDNs at runtime.

**Risk:**
- Supply-chain exposure.
- Lack of enterprise dependency control and change management.
- Runtime availability and integrity risks.

**Recommendation:**
- Vendor or internally host approved assets.
- Pin versions through approved build pipelines, not runtime remote imports.
- Avoid remote executable dependency fetches from the browser in enterprise UI code.

## Security Findings

### 6. Raw error rendering into preview DOM
**Severity:** Medium  
**Location:** iframe error handling `insertAdjacentHTML`

Errors are rendered directly into HTML using concatenated strings.

**Risk:**
- Leakage of internal implementation details.
- Error content may contain unexpected text that should not be inserted as HTML.

**Recommendation:**
- Render via safe text insertion rather than HTML concatenation.
- Use `textContent` or a controlled error node.
- Avoid exposing stack traces or verbose internals to end users.

---

### 7. Missing runtime input validation
**Severity:** Medium  
**Location:** component boundaries for `html`, `css`, `js`, `widgetActionHandlers`

The code normalizes nullish values to empty strings but does not validate schema, size, or allowed structure.

**Risk:**
- Oversized payloads, malformed data, and unexpected runtime behavior.
- Harder debugging and weaker resilience.

**Recommendation:**
- Add boundary validation for persisted/user-originated data.
- Enforce maximum sizes for HTML/CSS/JS payloads.
- Validate `widgetActionHandlers` structure before use.

---

### 8. Missing accessibility controls for modal
**Severity:** Low  
**Location:** `SculptModal`

The modal does not provide full dialog semantics or focus management.

**Risk:**
- Accessibility non-compliance.
- Poor keyboard and assistive technology support.

**Recommendation:**
- Add `role="dialog"`, `aria-modal="true"`.
- Implement focus trap and focus return.
- Ensure overlay/button semantics align with accessibility guidelines.

## Actionable Recommendations

### Immediate actions
1. **Rotate all exposed tokens and treat the prompt disclosure as a security incident.**
2. **Block production release of this preview implementation** until iframe isolation and remote code loading risks are addressed.
3. **Harden the message event listener** by validating message source and origin.
4. **Remove `allow-same-origin` and `allow-modals`** unless explicitly justified and documented.
5. **Stop loading executable compiler/runtime dependencies from public CDNs at runtime.**

1. Add runtime validation and length limits for `html`, `css`, `js`, and handler arrays.
2. Replace raw HTML-based error insertion with safe DOM text rendering.
3. Add accessibility semantics and focus management to the modal.
4. Split the file into smaller modules to improve testability.
5. Add React Testing Library + Vitest/Jest test coverage.

### Strategic actions
1. Define a secure architecture for custom-component previewing.
2. Establish a clear policy for untrusted code execution in frontend features.
3. Require acceptance criteria and defect traceability for broad bug-fix stories before implementation sign-off.
4. Enforce SDLC secret scanning and prompt/output redaction controls.

## Suggested Hardened Code Changes

### Safer message validation
```ts
useEffect(() => {
  const handleMessage = (event: MessageEvent): void => {
    if (event.source !== iframeRef.current?.contentWindow) return;
    if (event.data?.type !== "IFRAME_CLICK") return;
    onSelectRef.current?.();
  };

  window.addEventListener("message", handleMessage);
  return () => window.removeEventListener("message", handleMessage);
}, [onSelectRef]);
```

### Reduce sandbox permissions
```tsx
<iframe
  ref={iframeRef}
  style={{ width: "100%", height: "100%", border: "none" }}
  sandbox="allow-scripts"
  title="Sculpt Custom Component Preview"
/>
```

### Safe error rendering pattern inside iframe content
```js
const pre = document.createElement("pre");
pre.style.color = "red";
pre.style.whiteSpace = "pre-wrap";
pre.style.padding = "12px";
pre.style.margin = "0";
pre.textContent = String(err);
document.body.appendChild(pre);
```
