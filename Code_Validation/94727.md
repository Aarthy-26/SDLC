## Issues Found

1. **Potential information disclosure via reflected exception messages for generic 400s**
   - **Severity:** Medium
   - **Location:** `GlobalExceptionHandler.java` → `handleBadRequest(...)` and `safeMessage(...)`
     - `handleBadRequest(...)` returns `safeMessage(ex.getMessage(), "Invalid request")`
     - `safeMessage(...)` returns the **trimmed raw exception message** if present
   - **Why it matters (OWASP):** Can reflect internal/technical details (parameter formats, binding internals, downstream messages) back to clients. This is a common vector for **Information Disclosure** (OWASP A01/A05 depending on classification and context).
   - **Remediation:**
     - Prefer **fixed, client-safe** messages for generic bad requests; optionally add controlled structured details.
     - Example approach:
       - `IllegalArgumentException` → `"Invalid request"` (no raw message)
       - `MethodArgumentTypeMismatchException` → `"Invalid parameter format"` plus a safe `parameter` field
       - `ConstraintViolationException` → `"Request constraint violation"` plus sanitized `violations[]`
     - Consider introducing an **application error code registry** (enum/constants) to avoid ad-hoc strings.

2. **Brittle path extraction in overridden handler methods**
   - **Severity:** Low
   - **Location:** `GlobalExceptionHandler.java` → `extractPath(WebRequest request)`
   - **Issue:** Relies on `request.getDescription(false)` string format (e.g., `"uri=/api/widgets"`) and substring parsing.
   - **Impact:** Could produce unexpected `path` values under alternate `WebRequest` implementations or future Spring changes; weakens audit traceability.
   - **Remediation:**
     - Use `ServletWebRequest` (cast) and extract `((ServletWebRequest) request).getRequest().getRequestURI()`.
     - Or override handlers to accept `HttpServletRequest` where possible for consistent path extraction.

3. **Incomplete exception mapping coverage for common REST faults**
   - **Severity:** Low
   - **Location:** `GlobalExceptionHandler.java` (missing overrides/handlers)
   - **Gap examples:**
     - `HttpRequestMethodNotSupportedException` → should map to **405** with envelope
     - `NoHandlerFoundException` (if enabled) → should map to **404** with envelope
     - `BindException` (query/form binding) → should map to **400** validation envelope
   - **Remediation:**
     - Add overrides in `ResponseEntityExceptionHandler` for these types and return consistent `ApiErrorResponse`.
     - Document codes and expected HTTP statuses.

4. **Missing correlation/trace ID in response envelope and logs**
   - **Severity:** Medium
   - **Location:** Cross-cutting (`GlobalExceptionHandler.java`, logging strategy)
   - **Impact (SOC2):** Reduces incident response and audit traceability. Correlation IDs are often required by enterprise logging standards.
   - **Remediation:**
     - Add `traceId` (or `correlationId`) to `ApiErrorResponse`.
     - Populate from inbound headers (`traceparent`, `X-Correlation-Id`) or generate per request.
     - Add to MDC and include in logs.

5. **Test suite does not validate all envelope fields for every mapped error type**
   - **Severity:** Low
   - **Location:** `Unittest/94727.md` (tests included in `GlobalExceptionHandlerInventoryTest`)
   - **Observations:**
     - Good coverage for `VALIDATION_ERROR`, `MALFORMED_JSON`, `UNSUPPORTED_MEDIA_TYPE`, `WIDGET_NOT_FOUND`, and sanitized `INTERNAL_SERVER_ERROR`.
     - Missing explicit tests for: `MISSING_PARAMETER` mapping, and any added 405/404 handler gaps (see issue #3).
   - **Remediation:**
     - Add MockMvc tests for missing query parameter scenario and for method-not-allowed.
