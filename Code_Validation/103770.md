## Issues Found

### 1) Console logging used instead of enterprise logging framework
- **Severity:** Medium
- **Location:** `ProfilerApp.java` (main method, final line)
- **Criterion:** **E-LoggingFramework**
- **Finding:** Uses `System.out.println("Profiling completed...")`. Enterprise standards typically require an approved logging framework (SLF4J/Logback) with levels and structured context.
- **Remediation:** Replace `System.out.println` with SLF4J logger:
  - Add dependencies: `slf4j-api` + `logback-classic` (or org standard).
  - Log run metadata (runId, schema, table count, start/end timestamps) at INFO.
  - Avoid logging raw sampled values (see issue #2).

### 2) Potential sensitive data exposure via persisted “samples” in report
- **Severity:** Medium
- **Location:** `ProfilerApp.java`:
  - `findInvalidIso8601Samples(...)` adds raw invalid strings into `DataQualityIssue.samples`
  - `findUnmappedSensitivityCodes(...)` adds raw codes into `DataQualityIssue.samples`
  - Report written to `profiling-report.json`
- **Criterion:** **B-SensitiveDataExposure**
- **Finding:** Sample values may contain PII/secrets depending on source data. Persisting raw samples to disk can violate data minimization and retention expectations (SOC2/ISO27001).
- **Remediation:**
  - Default to **counts only** (no samples) and gate sampling behind config flag (env var like `PROFILER_INCLUDE_SAMPLES=false`).
  - Redact/mask samples (e.g., keep first/last 2 chars, or store hashes).
  - Apply file permission hardening (`rw-------`) where supported, and document retention policy.

### 3) Dynamic SQL string construction for identifiers (controlled) – document threat model
- **Severity:** Low
- **Location:** `ProfilerApp.java` multiple methods building SQL using `qualified` and `qIdent(...)`
- **Criterion:** **B-Injection**
- **Finding:** SQL is constructed via string concatenation for schema/table/column identifiers. Mitigated by:
  - fixed allowlist `TABLES`
  - identifiers from `DatabaseMetaData.getColumns`
  - `qIdent()` quoting/escaping
  This is **low risk** but should be explicitly documented as safe-by-construction.
- **Remediation:**
  - Add comments / docs stating identifiers are either constant allowlist or DB metadata, and are always quoted.
  - Keep `TABLES` immutable and avoid external input controlling identifiers.

### 4) Missing controlled top-level exception handling and exit codes
- **Severity:** Low
- **Location:** `ProfilerApp.java` `main(String[] args) throws Exception`
- **Criterion:** **B-SecurityMisconfiguration** (verbose errors) / **C-ExceptionHandling**
- **Finding:** `main` throws `Exception`; on failure, default JVM stack trace can be printed (depending on runner), which may expose internal details in logs/console.
- **Remediation:**
  - Wrap `main` body in try/catch:
    - log sanitized error summary
    - return non-zero exit code
    - optionally write partial report with failure metadata

### 5) Potential maintainability risk: complex/long method
- **Severity:** Medium
- **Location:** `ProfilerApp.java` method `profileTable(...)`
- **Criterion:** **C-MethodLength** / **C-CyclomaticComplexity**
- **Finding:** `profileTable` contains multiple responsibilities (null metrics, distinct, string lengths, timestamp anomaly detection, sensitivity validation, datetime ranges, mod_ref check). Cyclomatic complexity likely approaching or slightly exceeding **>10** depending on final compiled structure.
- **Remediation:**
  - Extract into smaller methods:
    - `computeNullMetrics`, `computeDistinctMetrics`, `computeStringMetrics`, `detectTimestampAnomalies`, `detectSensitivityCodes`, `computeTemporalRanges`, `detectMissingModRef`
  - This improves unit testability and reduces change risk.

### 6) Performance/operational risk: multiple full-table scans per column
- **Severity:** Medium
- **Location:** `ProfilerApp.java` `profileTable(...)`
- **Criterion:** **C-CodeQuality** (operability/maintainability) / **E-ConfigurationExternalized** (timeouts/limits)
- **Finding:** For each column, multiple queries are issued:
  - `COUNT(*)`, null count, `COUNT(DISTINCT ...)`, min/max length (strings), min/max datetime (temporal)
  This can be expensive on wide/large tables.
- **Remediation:**
  - Add configurable query limits/timeouts (e.g., `Statement#setQueryTimeout`, JDBC login timeout).
  - Consider consolidating metrics per table using dynamic SQL aggregation.
  - Consider sampling for distinct estimation or using PostgreSQL `pg_stats` where acceptable.

### 7) Temporal formatting inconsistency for TIME values
- **Severity:** Low
- **Location:** `ProfilerApp.java` `stringifyTemporal(Object o)`
- **Criterion:** **C-CodeQuality**
- **Finding:** `java.sql.Time` is a `java.util.Date` subtype; current code will hit `instanceof Date` branch and emit `Time.toString()` (not ISO-8601 time format with offset). Output may be inconsistent across temporal types.
- **Remediation:**
  - Add explicit handling for `java.sql.Time` / `LocalTime` and return ISO-8601 compatible time string.

### 8) Enterprise compliance gaps: license header and configuration externalization beyond DB
- **Severity:** Low
- **Location:** All source files
- **Criterion:** **E-LicenseHeader** / **E-ConfigurationExternalized**
- **Finding:**
  - No license/copyright header present (if organizational policy requires).
  - Output filename `profiling-report.json` and internal limits (`LIMIT 5000`, sample limits 10/20) are hardcoded.
- **Remediation:**
  - Add org standard header if required.
  - Externalize operational parameters via env vars or properties:
    - output path, sample sizes, scan row limit, table list override (optional), allowed sensitivity codes.
