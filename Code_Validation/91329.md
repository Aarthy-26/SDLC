User Story ID: 91329

Validation Summary: Fail — High-risk filesystem access controls missing; multiple medium-risk security/compliance gaps identified. Code is syntactically valid and generally well-structured, but not production/enterprise compliant as-is.

Issues Found:
1) Inadequate path traversal / arbitrary file access control
   Severity: High
   Location: AppEnhancementService.validatedPath(String) (src/main/java/com/ascendion/aava/jsonapp/service/AppEnhancementService.java)
   Finding: validatedPath() normalizes then checks path.toString().contains(".."). After normalization, ".." segments are typically removed, making the check ineffective. Also, absolute paths are allowed (e.g., "/etc/passwd" or "C:\\Windows\\...") which enables arbitrary file reads/writes when combined with readJson(), backupAndAtomicWrite(), and packageForDeployment() outputZip/backupDir usage.
   Remediation:
   - Introduce a configured base directory (e.g., "workspaceRoot") and enforce all file paths resolve under it:
     - Reject absolute paths from clients.
     - Resolve using baseDir.resolve(p).normalize().toRealPath(NOFOLLOW_LINKS) where appropriate.
     - Verify resolvedPath.startsWith(baseDirReal).
   - Prefer server-controlled filenames: accept only relative names, or lock appPath to a fixed "app.json".
   - Apply the same validation to backupDir and outputZipStr (currently unvalidated).

2) Unvalidated backupDir allows writing backups to sensitive locations
   Severity: High
   Location: AppEnhancementService.backupAndAtomicWrite(Path,ObjectNode,String)
   Finding: backupDir is taken from request and passed to Paths.get(backupDir) without scoping/allowlist. An attacker with API key can write backups to arbitrary directories, potentially overwriting or filling disks.
   Remediation:
   - Disallow client-provided backupDir or accept only a relative subdirectory name.
   - Enforce baseDir scoping and filename restrictions.
   - Add a maximum number/age policy for backups.

3) Unvalidated outputZipStr enables arbitrary file write
   Severity: High
   Location: AppEnhancementService.packageForDeployment(String,String)
   Finding: outputZipStr is used directly to create directories and write a ZIP. This can overwrite sensitive files or write into protected areas if service permissions allow.
   Remediation:
   - Do not accept arbitrary output paths from the client.
   - Enforce baseDir scoping, reject absolute paths, restrict extensions to .zip, and set a fixed output directory.

4) Transport security and exposure controls are insufficient
   Severity: High
   Location: application.properties / deployment configuration; ApiKeyFilter
   Finding: Service listens on HTTP and default address (likely 0.0.0.0 depending on environment). API key alone is not sufficient if exposed beyond localhost.
   Remediation:
   - Bind to localhost by default: server.address=127.0.0.1
   - If remote use is needed: enable TLS (Spring Boot SSL), and consider mTLS/OAuth2.
   - Document threat model and ensure firewalling.

5) Missing request size limits (DoS risk)
   Severity: Medium
   Location: AppController endpoints (/plan, /apply, /package), Jackson/Tomcat configuration
   Finding: No explicit limits for request body size, JSON depth, or number of patch operations. Large payloads may cause memory/CPU pressure.
   Remediation:
   - Configure server limits (Tomcat maxPostSize/maxSwallowSize).
   - Configure Jackson StreamReadConstraints (max depth, max string length) in Spring Boot 3.
   - Enforce max patch operation count and max requirementText length.

6) Missing rate limiting / brute-force protection
   Severity: Medium
   Location: ApiKeyFilter
   Finding: Unlimited auth attempts; susceptible to brute force and abuse.
   Remediation:
   - Add rate limiting (Bucket4j filter, Spring Cloud Gateway, or a servlet filter).
   - Implement exponential backoff or temporary blocks per IP.

7) Sensitive information exposure via absolute paths in responses
   Severity: Medium
   Location: ApplyChangesResponse (backupPath/appPath), PackageResult.bundlePath returned from /package
   Finding: Returns absolute filesystem paths to clients, revealing directory structure.
   Remediation:
   - Return relative identifiers/filenames, or mask base directories.
   - Provide a configuration switch to suppress path echoing.

8) /package uses Map<String,Object> without validation
   Severity: Medium
   Location: AppController.packageApp(@RequestBody Map<String,Object>)
   Finding: Untyped map bypasses bean validation; no length/pattern constraints.
   Remediation:
   - Replace with a DTO record, e.g., PackageRequest(@NotBlank String appPath, String outputZip)
   - Add validation for length and allowed patterns.

9) Audit logging gaps (insufficient monitoring/traceability)
   Severity: Medium
   Location: GlobalExceptionHandler, ApiKeyFilter, service layer
   Finding: Exceptions are not logged; auth failures and file operations are not audit-logged. This impacts SOC2-style monitoring requirements.
   Remediation:
   - Add structured logs (JSON) with correlation/request IDs.
   - Log security events (auth failure, validation failure, file write) WITHOUT logging API keys or full request bodies.
   - Consider adding an audit event sink.

10) Regex compilation strategy (minor perf/DoS hygiene)
   Severity: Low
   Location: RegexUtil.firstGroup
   Finding: Patterns are compiled on every call. While patterns are currently simple and bounded, repeated compilation is inefficient and could be risky if patterns become complex.
   Remediation:
   - Precompile known patterns as static final Pattern constants.
   - Enforce maximum requirementText length.

11) Dead/unused code
   Severity: Low
   Location: AppEnhancementService.generatePlan(): patchWrapper is created but never used.
   Remediation:
   - Remove patchWrapper or return it consistently if desired.
