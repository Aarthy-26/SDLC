## Issues Found

### 1) Unrestricted Actuator/Prometheus endpoint exposure
- **Severity:** High
- **Location:** `src/main/resources/application.properties`
  - `management.endpoints.web.exposure.include=health,info,metrics,prometheus`
  - `management.endpoint.prometheus.access=unrestricted`
- **Risk / OWASP Mapping:**
  - **OWASP A01: Broken Access Control** (monitoring endpoints exposed without access control)
  - Also operational intelligence leakage (metrics can reveal topology, performance characteristics, and usage patterns)
- **Remediation:**
  - Do not set `management.endpoint.prometheus.access=unrestricted` in production.
  - Restrict actuator endpoints via Spring Security (role-based) and/or network controls (internal-only, IP allowlist).
  - Prefer a separate management port and internal bind:
    - `management.server.port=8081`
    - `management.server.address=127.0.0.1` (or internal interface)
  - Reduce exposure list to minimum needed.
- **Compliance Impact:**
  - **SOC2 (Security/Confidentiality): Non-compliant** unless protected.
  - Potentially conflicts with internal hardening baselines and monitoring data protection requirements.

### 2) Thread pool created inside service with no lifecycle management
- **Severity:** High
- **Location:** `ProjectDetailsService` constructor
  - `this.executor = Executors.newFixedThreadPool(...)`
- **Risk:**
  - Thread/resource leak on application redeploy/shutdown (no `shutdown()`/`awaitTermination()`)
  - Harder to tune and observe; no queue bounds or rejection policy
  - Availability risk under load (possible request amplification + thread starvation)
- **Remediation:**
  - Inject a managed executor bean (preferred):
    - `ThreadPoolTaskExecutor` (Spring) with bounded queue, naming, rejection policy, graceful shutdown.
  - Or add lifecycle hook:
    - `@PreDestroy` method calling `shutdown()` and `awaitTermination()`.
  - Consider Resilience patterns (bulkhead/circuit breaker) for real downstream calls.
- **Compliance Impact:**
  - **SOC2 (Availability): Partially compliant → needs remediation**

### 3) Potential DoS / thread exhaustion due to per-request async submission + blocking wait
- **Severity:** Medium
- **Location:** `ProjectDetailsService.callDownstreamWithTimeout()`
  - `executor.submit(...)` then `future.get(timeoutMillis, ...)`
- **Risk:**
  - Under high concurrency, requests may accumulate waiting on limited worker threads.
  - Even with timeouts, queue growth and contention can create latency spikes.
- **Remediation:**
  - For real downstream integrations, prefer non-blocking I/O (`WebClient`) with connect/read timeouts.
  - If blocking is required, use bounded queues and explicit rejection (`CallerRunsPolicy`/custom) and apply bulkheads.
  - Add concurrency tests and load tests.
