- **Remediation:**

### 3) Logging framework not used (System.out/System.err used by intended design)
- **Severity:** Low
- **Location:** Intended implementation (per requirements/tests); currently placeholder file
- **Criterion:** E-LoggingFramework
- **Details:** Enterprise standards typically require SLF4J/Log4j rather than `System.out`/`System.err`. The expected design uses stdout for output YAML and stderr for audit log.
- **Remediation:**
  - For a CLI tool, stdout/stderr separation is acceptable, but consider:
    - Using a logging framework for audit logs (stderr handler) with structured output.
    - Providing `--audit-format json` for machine-readable audit events.

### 4) YAML parsing is heuristic (correctness risk)
- **Severity:** Medium
- **Location:** Intended implementation (not present in repo)
- **Criterion:** C-CodeQuality & D-JavaBestPractices (robust parsing)
- **Details:** The described approach removes keys under `data:` by scanning lines. This is not a full YAML parser and may mis-handle complex YAML constructs (anchors, quoted keys with `:`, multi-doc YAML, indentation edge cases).
- **Remediation:**
  - If strict YAML compliance is required, use a YAML parser (e.g., SnakeYAML Engine).
  - If “preserve formatting” is required, document supported YAML subset and add tests for the supported subset.

### 5) Potential metadata exposure via audit log (key names)
- **Severity:** Medium
- **Location:** Intended `audit(...)` output (stderr)
- **Criterion:** B-SensitiveDataExposure
- **Details:** Even if values are not logged (good), key names can sometimes reveal sensitive intent (e.g., `SECRET_KEY`).
- **Remediation:**
  - Add a `--redact-keys` default behavior (hash or mask key names), and allow `--verbose` for full key names when authorized.
  - Continue to **never** log values.
