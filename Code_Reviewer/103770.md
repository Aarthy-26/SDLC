User Story ID: 103770
Review Summary: Overall solid, secure-by-default console profiling utility (Java 17, JDBC, env-based secrets). No critical injection vectors observed and resources are generally handled correctly via try-with-resources. Primary gaps are enterprise logging/auditability (System.out/err), potential operational/performance risks due to N×M counting queries, and minor maintainability concerns from a single-file “multi-class” design that may evolve into a God Class as requirements expand.

Findings:
Issue: Console logging via System.out/System.err instead of approved logging framework (e.g., SLF4J + Logback) and no structured audit logging for sensitive operations (DB connect, profiling start/end, tables scanned).
Severity: Medium
Recommendation: Replace System.out/err with SLF4J; add an audit logger/channel with structured events (start/end, schema, tables, orphan checks executed, row counts, exceptions with safe messages). Ensure logs avoid secrets/PII and support SOC2 audit trails.
Compliance Impact: SOC2 risk—insufficient audit logging/traceability for data access and diagnostic operations.

Issue: Potential performance/operational risk due to large number of full-table scans (per table: COUNT(*), per column: COUNT NULLs, COUNT DISTINCT, MIN/MAX LENGTH, MIN/MAX date). On wide tables this becomes many queries and can be expensive on production-like datasets.
Severity: Medium
Recommendation: Optimize by batching metrics per table (single query with multiple aggregates where feasible), sampling strategy, configurable column include/exclude lists, and/or execution limits/timeouts. Consider using PostgreSQL statistics (pg_stats) for approximations or enable a “fast mode”. Add statement/query timeouts.
Compliance Impact: Indirect SOC2 availability concern—heavy scans can impact shared DB performance and availability.

Issue: SQL is assembled via string concatenation for identifiers (schema/table/column), albeit from internal constants/meta-data, and then quoted by qIdent(). This is not SQL-injection in the typical sense, but still a hardening opportunity; also meta-derived identifiers could be unexpected in hostile DB contexts.
Severity: Low
Recommendation: Keep qIdent(), but additionally validate identifiers against a strict allowlist/regex (e.g., ^[A-Za-z_][A-Za-z0-9_]*$) before quoting. Keep table list as a strict allowlist (already done). Avoid accepting schema/table names from user input.
Compliance Impact: General secure coding hardening; no direct PCI/SOC2 violation observed.

Issue: main() is doing multiple responsibilities (config loading, DB connection, orchestration, output). File also contains multiple DTOs, helper records, and logic; while currently under “God class” thresholds, it trends toward a monolith.
Severity: Low
Recommendation: Split into packages/classes: config (EnvConfig), db (JdbcClient), profiling (TableProfiler), diagnostics (DiagnosticsRunner), reporting (JsonReporter), dto (Report DTOs). Improves testability and separation of concerns.
Compliance Impact: None direct; improves maintainability and change control (SOC2 SDLC practices).

Issue: Missing consistent null-handling semantics in some helper methods: queryForMinMaxLong casts rs.getObject() to Long directly; some JDBC drivers may return Integer/BigDecimal depending on expression/type.
Severity: Medium
Recommendation: Use rs.getLong with rs.wasNull() checks, or cast via Number: Number n=(Number)rs.getObject(1); Long min=n==null?null:n.longValue(); same for max. Add tests across drivers.
Compliance Impact: Reliability/accuracy risk; could affect audit/report correctness.

Issue: Error handling: requireEnv throws IllegalStateException which is not caught in main; user gets stack trace by default (depending on runtime) and exit code might be 1 without controlled message.
Severity: Medium
Recommendation: Catch RuntimeException/IllegalStateException in main, print a safe one-line message, and exit with distinct code. Use logger; avoid printing stack traces to stdout/stderr in production.
Compliance Impact: SOC2—improper error handling may leak internals; operational consistency.

Issue: No explicit TLS enforcement/verification for DB_URL (depends on environment). Many enterprises require sslmode=require/verify-full for Postgres.
Severity: Medium
Recommendation: Document and/or validate DB_URL includes sslmode=require (or verify-full with proper certs). Optionally fail fast if sslmode is missing in production mode.
Compliance Impact: PCI-DSS/SOC2—encryption in transit expectation; depends on data classification.

Issue: Diagnostic sampling for timestamp-like strings uses LIMIT 5000 distinct values; results may undercount invalids and could miss issues.
Severity: Low
Recommendation: Make sampling size configurable and/or implement server-side regex-based counting for accuracy (e.g., COUNT(*) FILTER (WHERE col !~ 'regex') ), with safeguards for large tables.
Compliance Impact: Data quality/completeness; not a direct regulatory breach.

Issue: Javadoc present on class and some DTOs but not on most public methods/classes (DTO getters/setters). Enterprise standards often require Javadoc for public API surface.
Severity: Low
Recommendation: Add Javadoc to public methods or reduce visibility (package-private) where not intended as API. Consider Lombok or records for DTOs if acceptable.
Compliance Impact: Internal style guide adherence.

Issue: No explicit data retention/purge behavior for generated report file; report may contain sensitive operational metadata (row counts, distinct values counts) and potentially sensitive field names.
Severity: Medium
Recommendation: Add guidance/config for retention (e.g., write to a controlled directory, optional encryption at rest, TTL cleanup). Ensure report does not include raw data values (currently it does not).
Compliance Impact: SOC2—data retention and handling policies; PCI-DSS if future expansions include PAN/CVV-related profiling.
