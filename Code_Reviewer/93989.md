User Story ID: 93989
Review Summary: Overall code quality is good (clear structure, separation of concerns, unit tests for validators, env-based secret handling). However, several enterprise/security gaps exist: potential sensitive data exposure via error payload storage/exception messages, incomplete URL/path encoding, lack of TLS/certificate pinning guidance, missing structured logging/audit controls, and incomplete compliance considerations for handling generated artifacts (BIM/base64 content) and third-party API usage.

Findings:
- Issue: Potential sensitive data exposure by storing full non-2xx response payload in ClaudeApiException (responseBody) and including truncated payload in exception message
  Severity: High
  Recommendation: Do not persist raw response bodies by default. Store only correlation/request ID and sanitized error summary. If body must be retained for debugging, gate behind an explicit debug flag and redact secrets/PII. Avoid embedding response payload into exception messages that may be logged.
  Compliance Impact: SOC2 (confidentiality/logging), internal policies on sensitive data handling; potential PCI-DSS impact if API ever returns PAN/auth tokens (avoid logging/retaining).

- Issue: API key is sent via custom header "X-API-Key" with no support for standard Authorization schemes and no explicit redaction protections in logs
  Severity: Medium
  Recommendation: Prefer standard Authorization header (e.g., "Authorization: Bearer <token>") if supported by the API. Add an HTTP logging policy that explicitly redacts authentication headers. Document operational guidance: never log environment variables or request headers.
  Compliance Impact: SOC2 (secrets management, operational security); internal secure coding standards.

- Issue: Incomplete URL path encoding in urlPathEscape (replaces only '/' and '\\')
  Severity: Medium
  Recommendation: Use a proper encoder for path segments (e.g., URLEncoder is for query, not path; consider building URI with URI components or percent-encoding all reserved chars). Validate agentId to a strict pattern (e.g., UUID/base64url) and reject unexpected characters.
  Compliance Impact: SOC2 (input validation), OWASP ASVS 5 (validation) / injection prevention.

- Issue: Missing explicit TLS/HTTPS enforcement and hostname verification expectations
  Severity: Medium
  Recommendation: Enforce https scheme in config unless explicitly allowed for non-prod (reject http by default). Document certificate validation expectations; consider allowing custom truststore via JVM args rather than disabling verification.
  Compliance Impact: SOC2 (transmission security), PCI-DSS (strong cryptography in transit when applicable).

- Issue: App main uses System.out prints and lacks structured logging, correlation IDs, and audit events for create/run actions
  Severity: Medium
  Recommendation: Introduce a logging facade (SLF4J + Logback) with structured logs. Emit audit events for: config loaded (without secrets), agent created (id), agent run started/completed (id/status), validation result. Include a run/session ID for traceability.
  Compliance Impact: SOC2 (auditability, monitoring), internal audit logging policy.

- Issue: No retry/backoff strategy, no rate-limit handling, and no idempotency considerations
  Severity: Medium
  Recommendation: Implement bounded retries with exponential backoff for transient failures (5xx, timeouts). Respect Retry-After headers. Consider idempotency keys for create/run if supported by the API.
  Compliance Impact: SOC2 availability/reliability controls.

- Issue: Output validation is minimal and not schema-specific; output is typed as Object, increasing ambiguity and reducing safety
  Severity: Low
  Recommendation: Model output schema(s) explicitly (e.g., BIMOutput {fileName, contentType, contentBase64, summary} and LayoutOutput {layoutId, version, fields, summary}). Validate required fields, base64 correctness, size limits, and contentType allowlist.
  Compliance Impact: Internal quality standards; supports SOC2 change management and data handling controls.

- Issue: No safeguards for large responses (memory pressure) and no maximum payload size controls
  Severity: Medium
  Recommendation: Use BodyHandlers.ofInputStream() and stream with explicit max size or implement a size-limited subscriber. Enforce output size limits, especially for base64 BIM content.
  Compliance Impact: SOC2 availability (DoS resistance), internal resilience standards.

- Issue: Json utility uses a global ObjectMapper without additional hardening (e.g., time/module configuration) and throws IllegalArgumentException for parse errors
  Severity: Low
  Recommendation: Consider configuring ObjectMapper explicitly for JavaTimeModule if needed and keep failures as checked/typed exceptions (domain-specific) to improve error handling. Avoid leaking raw parse error details in external-facing logs.
  Compliance Impact: Internal error handling/logging standards.

- Issue: Maven build lacks common enterprise plugins (enforcer, dependency-check, spotbugs, checkstyle) and does not pin plugin versions beyond surefire
  Severity: Medium
  Recommendation: Add maven-enforcer-plugin (Java version, dependency convergence), OWASP dependency-check, SpotBugs/PMD/Checkstyle, and optionally surefire/failsafe separation. Consider generating SBOM (CycloneDX).
  Compliance Impact: SOC2 (vulnerability management), internal SDLC compliance.

- Issue: Tests cover validators only; no tests for ClaudeApiClient behavior (serialization, error handling, header setting)
  Severity: Low
  Recommendation: Add unit tests with a mock HTTP server (e.g., WireMock or JDK HttpServer) to verify requests, headers, timeouts, and non-2xx handling with redaction.
  Compliance Impact: Internal QA standards; SOC2 change quality.
