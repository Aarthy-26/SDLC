User Story ID: 101046
Review Summary: Overall code quality is strong and largely aligns with enterprise secure-coding expectations for a small CLI utility. No hardcoded secrets were found and logging is generally safe. Primary gaps are: (1) the read-back verification performs a secret read (could increase exposure risk in memory/audit trails) and (2) transport security is not explicitly enforced (TLS required; ideally restrict to https and optionally implement cert pinning/enterprise truststore). Compliance-wise, no direct PCI-DSS card data is handled, but SOC2 expectations around auditability and access control should be reinforced via Vault policy/role constraints and explicit audit logging guidance.

Findings:
Issue: Secret verification reads back secret value (KV read returns full secret, stored in-memory)
Severity: Medium
Recommendation: Replace `readSecret()` verification with a metadata-only check. For Vault KV v2, call `/v1/<mount>/metadata/<path>` (or a dedicated `readSecretMetadata()` API) to confirm existence/version without retrieving the secret value. If you must read, immediately discard and avoid retaining the value; consider verifying write via HTTP status only.
Compliance Impact: SOC2 (confidentiality) — unnecessary retrieval increases exposure surface and may increase audit scope if secrets appear in traces/dumps. Not a PCI-DSS issue unless the token grants access to card data.

Issue: Transport security not explicitly enforced beyond URI scheme validation
Severity: High
Recommendation: Enforce `https` only for `VAULT_ADDR` in non-dev environments (INT included, per policy). Add optional configuration for TLS settings (trusted CA bundle / corporate truststore) and consider hostname verification defaults. Document required TLS versions (TLS 1.2+). If policy requires, implement mTLS.
Compliance Impact: SOC2 Security — encryption in transit requirement; internal policies typically mandate TLS. Potential compliance breach if `http://` is used.

Issue: Exception handling in main catches generic `Exception` and exits; limited diagnostic context
Severity: Medium
Recommendation: Catch more specific exceptions where possible (`IllegalArgumentException`, `VaultClientException`) and log structured context (Vault path, kv version, status code if available) without secrets. Consider returning distinct exit codes for configuration vs connectivity vs authorization failures.
Compliance Impact: SOC2 Availability/Monitoring — improved diagnosability supports operational controls and incident response.

Issue: Potential sensitive data leakage through Vault error body echo (even though truncated)
Severity: Medium
Recommendation: Current `sanitizeVaultError()` truncates to 512 chars but still may include request identifiers or echoed inputs depending on upstream proxies. Consider stricter filtering (e.g., allowlist JSON fields like `errors`) or replace with generic message + correlation id. Ensure debug logging is disabled in production.
Compliance Impact: SOC2 Confidentiality — reduce risk of leaking sensitive context in logs.

Issue: Missing explicit timeouts/retry/backoff strategy for transient Vault failures
Severity: Low
Recommendation: Add a small retry policy with exponential backoff for idempotent operations (read/metadata) and/or handle common transient codes (429, 503). Keep write retries conservative to avoid accidental multiple versions if not desired.
Compliance Impact: SOC2 Availability — improves resilience.

Issue: No Javadoc on some public methods in VaultClient (public API surface)
Severity: Low
Recommendation: Add Javadoc for `create`, `loginWithAppRole`, `writeSecret`, `readSecret` describing thread-safety, expected exceptions, and KV v1/v2 behavior.
Compliance Impact: Internal engineering standards — improves maintainability and auditability of intended behavior.

Issue: KV v2 path helper edge case when only mount provided
Severity: Low
Recommendation: In `toKv2DataPath()`, when only mount is provided, returning `mount + "/data"` likely isn’t a valid secret path. Consider rejecting mount-only paths with a clear error for KV v2.
Compliance Impact: None direct; reduces operational misconfiguration risk.

Issue: Logging includes secret path; path may be considered sensitive in some organizations
Severity: Low
Recommendation: If Vault paths are classified, log a redacted/hashed path or categorize by system (e.g., “databricks-agent-token path”). Otherwise acceptable.
Compliance Impact: SOC2 Confidentiality (contextual) — depends on internal classification.
