Findings:
- Issue: DTO mutability introduced (no-args constructor + setters)
  Severity: Low
  Recommendation: If immutability is desired, consider an alternative pattern using `@JsonCreator` with a canonical constructor (or Java record) and `@JsonProperty` annotations, while keeping backward compatibility. If setters are acceptable per enterprise DTO guidelines, document that DTOs are mutable by design.
  Compliance Impact: Low; internal code quality guidelines (immutability preference) only.

- Issue: `@JsonProperty` annotations on fields are redundant with standard Jackson naming
  Severity: Low
  Recommendation: Remove redundant `@JsonProperty` annotations unless required for non-standard names or to lock down schema; keep `@JsonIgnoreProperties(ignoreUnknown = true)` as it supports forward compatibility.
  Compliance Impact: None.

- Issue: Missing bean validation / domain constraints on DTO fields (e.g., `name` non-blank, `length` non-negative)
  Severity: Medium
  Recommendation: If `ColumnResponse` is used as an API boundary DTO, add Jakarta Bean Validation annotations (e.g., `@NotBlank`, `@NotNull` where applicable, `@Min(0)` for `length`) and validate at controller/service boundary. If it’s an internal DTO only, ensure upstream validation exists.
  Compliance Impact: SOC2 / internal reliability controls: Medium (input validation expectations).

- Issue: Unit test duplicates configuration (`FAIL_ON_UNKNOWN_PROPERTIES` set while class already ignores unknown)
  Severity: Low
  Recommendation: Prefer one consistent approach. Since the DTO has `@JsonIgnoreProperties(ignoreUnknown = true)`, the mapper configuration line can be removed from `shouldDeserializeColumnResponse()` to keep the test focused on DTO behavior.
  Compliance Impact: None.

- Issue: `equals` uses `getClass()` instead of `instanceof`, which can be problematic with proxies/subclasses
  Severity: Low
  Recommendation: Keep as-is for DTOs if subclassing is not expected. Otherwise, use `instanceof` and pattern matching. For DTOs, final classes are often preferred.
  Compliance Impact: None.

- Issue: `toString()` includes all fields; potential sensitive data exposure if DTO later includes sensitive columns
  Severity: Low
  Recommendation: For DTOs used in logs, ensure sensitive fields are redacted if added in future. Consider omitting potentially sensitive fields from `toString()` or using a structured logging policy.
  Compliance Impact: SOC2 logging/data minimization: Low (future-proofing).
