User Story ID: 111233
Review Summary: Overall code quality is good and largely aligns with Spring/JdbcTemplate enterprise patterns; primary gaps are access-control assumptions around the SSO endpoint, potential account-linking risk via email fallback, missing centralized exception handling, and minor layering/style issues (repository annotated as @Service, wildcard SELECT, lack of audit logging).

Findings:
Issue: Potential broken access control / trust boundary assumption for /api/auth/sso/resolve-user (endpoint can provision/resolve users based solely on request body)
Severity: High
Recommendation: Ensure the endpoint is only callable after verified SSO authentication. Enforce Spring Security constraints (e.g., require authenticated principal with an SSO-authenticated token/claim), and do not accept username/email solely from the body; instead, derive them from the validated IdP assertion (OIDC id_token claims) or server-side session. Add authorization checks and anti-CSRF measures as appropriate.
Compliance Impact: SOC2 risk (insufficient access control for account provisioning and identity operations). Could also become a PCI-DSS scope expansion risk if unauthorized provisioning leads to access to cardholder-adjacent systems.

Issue: Account linking risk via email fallback (findByEmailIgnoreCase) could allow unintended takeover/merging if email is not strongly verified/unique
Severity: High
Recommendation: Only allow email fallback if the IdP provides a verified email claim (email_verified=true) and you have deterministic tenant/issuer binding (issuer + subject). Prefer linking on immutable IdP subject (sub) + issuer rather than email. If fallback is required, require additional checks: existing user_source==SSO with same issuer, or an explicit user-driven linking flow.
Compliance Impact: SOC2 (identity integrity, unauthorized access). Potential privacy incident if accounts are cross-linked.

Issue: Missing audit logging for sensitive operation (user resolution/provisioning)
Severity: Medium
Recommendation: Add structured audit logs (via SLF4J) for: resolve attempt, existing-user reuse, new-user provisioning, and constraint-violation retry. Include correlation/request ID, IdP issuer, subject, and outcome. Do NOT log raw tokens, secrets, or full PII; consider hashing username/email or logging only userId.
Compliance Impact: SOC2: Not met for auditability expectations around authentication and account provisioning.

Issue: No centralized exception handling; IllegalArgumentException/IllegalStateException may leak internal details or produce inconsistent API responses
Severity: Medium
Recommendation: Add a @ControllerAdvice to map validation errors to 400 with sanitized messages, and unexpected errors to 500 with generic message. Ensure stack traces are not returned to clients. Consider a domain exception (e.g., SsoProvisioningException) with safe error codes.
Compliance Impact: SOC2 (operational security) and general secure error handling best practices.

Issue: Repository annotated as @Service instead of @Repository; can affect exception translation semantics and layering clarity
Severity: Low
Recommendation: Change SsoUserRepository annotation to @Repository. Keep service layer as @Service. This improves readability and leverages Spring’s persistence exception translation conventions.
Compliance Impact: None direct; internal standards/maintainability.

Issue: SELECT * usage in queries (findByUsername/findById)
Severity: Low
Recommendation: Select explicit columns needed by UserModel mapping to reduce coupling to schema changes and avoid accidentally pulling sensitive columns. Example: SELECT id, username, password, email, enabled, created_at FROM dpai.users WHERE username = ?
Compliance Impact: Supports least-privilege data minimization (SOC2 privacy principle depending on policy).

Issue: Input validation is basic; username normalization and constraints are minimal
Severity: Medium
Recommendation: Define and enforce username constraints (length, allowed chars), and normalize consistently (e.g., case sensitivity rules). Use Bean Validation (@Valid, @NotBlank, @Email) on the request record and add @Validated on controller/service.
Compliance Impact: SOC2 (defense-in-depth); reduces risk of unexpected inputs.

Issue: Null handling and API contract: request can be null, and request.username()/email() would NPE
Severity: Low
Recommendation: Add null check for request or enforce validation with @Valid and non-nullable JSON schema. Example: if (request == null) throw new IllegalArgumentException("Request body is required");
Compliance Impact: None.

Issue: Concurrency handling relies on DataIntegrityViolationException without verifying the violated constraint; may mask other integrity issues
Severity: Medium
Recommendation: Inspect exception cause/SQLState to ensure it’s the expected unique constraint (username) before retrying. Otherwise rethrow or wrap. Optionally use INSERT ... ON CONFLICT DO NOTHING then SELECT.
Compliance Impact: SOC2 (reliability) and operational robustness.

Issue: Password stored as NULL for SSO users may violate existing schema constraints and could impact authentication logic if other flows assume non-null
Severity: Medium
Recommendation: Confirm schema and authentication code paths. If password must be non-null, store a strong random value (SecureRandom) and mark account as SSO-only, or separate credentials into an auth table. Ensure login endpoints cannot authenticate SSO accounts via password.
Compliance Impact: SOC2 (auth correctness). If mishandled, could become access control weakness.

Issue: Lack of DTO/entity separation in API response (returns UserModel directly)
Severity: Medium
Recommendation: Return a dedicated DTO (e.g., UserDto) that excludes sensitive fields (password hash, internal flags). Ensure ApiResponse never serializes password.
Compliance Impact: SOC2 privacy; reduces risk of sensitive data exposure.

Issue: Missing Javadoc on public endpoint method; class is non-public and contains multiple nested types (single-file god-object tendency as it grows)
Severity: Low
Recommendation: Split into separate files/packages following controller/service/repository layering. Add Javadoc to public controller methods describing security requirements (SSO-authenticated only).
Compliance Impact: Internal standards.
