User Story ID: 81569

Review Summary: Overall implementation is clean, readable, and aligns well with the user story’s draft/approval/versioning and audit trail requirements. Core workflow controls (draft preserved until approval, submitter cannot approve, mandatory comment, impact acknowledgement gate) are implemented. However, there are several enterprise/security/compliance gaps typical of “demo auth” solutions: lack of real authentication/authorization framework, insufficient immutability guarantees for audit data, missing concurrency controls that could violate single-LIVE/single-pending-draft invariants, and potential sensitive data exposure through endpoints returning full content and impactAnalysisJson.

Findings:

- Issue: Demo authentication/authorization via headers is not secure (X-User-Id / X-User-Roles are caller-controlled)
  Severity: High
  Recommendation: Replace header-based identity/roles with Spring Security (OAuth2/JWT, mTLS, or corporate SSO). Enforce roles server-side from signed tokens/claims, and implement least-privilege authorization checks.
  Compliance Impact: SOC2 (Access Control), ISO 27001 (A.5/A.8), internal security policies typically require strong authn/authz; PCI-DSS if any cardholder-impacting workflow exists would require strong access control and audit integrity.

- Issue: Missing concurrency controls can allow race conditions (multiple pending drafts or multiple LIVE versions)
  Severity: High
  Recommendation: Add optimistic locking (@Version) to ArtifactVersion (and potentially Artifact). Add DB constraints:
    - Unique partial index: one LIVE per artifact
    - Unique partial index: at most one pending_approval=true per artifact
    Use SERIALIZABLE isolation or explicit locking (SELECT ... FOR UPDATE) around approval transitions.
  Compliance Impact: SOC2 (Change management integrity), internal governance controls—incorrect state transitions can break auditability and approval guarantees.

- Issue: LIVE version is demoted to IN_REVIEW on approval (potential semantic mismatch)
  Severity: Medium
  Recommendation: Consider a clearer lifecycle: previous LIVE -> APPROVED/HISTORICAL/SUPERSEDED rather than IN_REVIEW. IN_REVIEW commonly implies “awaiting review,” which is not true for an already-live, previously approved version.
  Compliance Impact: Internal policy/SDLC controls—status semantics matter for audits and evidence.

- Issue: Audit log immutability not enforced beyond “no API delete/update”
  Severity: High
  Recommendation: Enforce append-only at the database level:
    - Remove delete privileges for the audit table user
    - Add DB trigger to prevent UPDATE/DELETE
    - Add checksum/hashing chain (optional) to detect tampering
    Also ensure audit entries include request correlation ID and source IP (if permitted) for forensic traceability.
  Compliance Impact: SOC2 (Audit logging integrity), PCI-DSS Req 10 (if applicable), internal audit requirements for immutable logs.

- Issue: Sensitive data exposure risk through responses returning full content and impact analysis JSON
  Severity: High
  Recommendation: Apply data minimization:
    - For list endpoints, omit large LOB fields (content/impactAnalysisJson) unless explicitly requested and authorized
    - Add field-level authorization (e.g., only approvers/admins can view draft content)
    - Consider redaction/masking for impact analysis if it can include sensitive internal IDs
  Compliance Impact: SOC2 (Confidentiality), internal data handling policies; potential privacy obligations depending on data stored.

- Issue: Missing explicit validation of impactAnalysisJson structure/content
  Severity: Medium
  Recommendation: Validate impactAnalysisJson as JSON and enforce schema (e.g., Jackson parse + JSON schema validation). Also enforce the requirement: “Impact analysis lists must exclude dependent artifacts in Draft/In Review and include only approved versions.” Currently it is treated as an opaque string and never verified.
  Compliance Impact: Governance/SDLC compliance—workflow requirement not fully enforced; audit evidence may be challenged.

- Issue: Incomplete enforcement of “submitter excluded” beyond acknowledge/approve/reject
  Severity: Low
  Recommendation: Consider whether submitter should be able to call endpoints that reveal approver-only data (e.g., audit or draft details) and implement policy accordingly.
  Compliance Impact: Internal segregation-of-duties controls.

- Issue: No request correlation / audit session identifiers
  Severity: Medium
  Recommendation: Add a correlation ID (e.g., X-Correlation-Id) generated if absent; include it in AuditEntry. Log correlation ID in application logs for end-to-end traceability.
  Compliance Impact: SOC2 (Monitoring and logging), incident response readiness.

- Issue: Missing rate limiting / abuse protection on write endpoints
  Severity: Medium
  Recommendation: Add throttling (Spring Cloud Gateway, Bucket4j, or API gateway policies) and basic anti-automation controls if exposed beyond trusted network.
  Compliance Impact: SOC2 availability/security, internal platform standards.

- Issue: Potential IDOR/authorization gaps for read endpoints
  Severity: Medium
  Recommendation: Ensure GET endpoints (versions/audit) enforce authorization. Currently, live/version/audit endpoints do not require headers and allow unauthenticated reads depending on deployment configuration.
  Compliance Impact: SOC2 confidentiality; internal security policy.

- Issue: Use of create-drop DDL and enabled H2 console in application.yml
  Severity: Medium
  Recommendation: For non-demo environments: disable H2 console, use ddl-auto=validate or migrations (Flyway/Liquibase), externalize secrets, and enforce secure configs by profile.
  Compliance Impact: SOC2 change management and secure configuration baselines.

- Issue: Lack of explicit transaction boundary for review() method (private) with multi-entity state changes
  Severity: Low
  Recommendation: review() is called from @Transactional methods, so it participates; however, consider making it package-private and annotated or ensure no future refactor bypasses transaction boundaries.
  Compliance Impact: Internal reliability controls.
