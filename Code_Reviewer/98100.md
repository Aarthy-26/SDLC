Review Summary: Overall strong implementation with clear separation of concerns (row model vs selection model) and correct single-selection (radio-group) semantics. Security risk surface is low (console app, no persistence/network), with minor hardening opportunities around resource handling, output handling, and API design for UI embedding. Compliance posture is generally acceptable for SOC2/internal secure coding; PCI-DSS is not directly applicable because no cardholder data is handled.

Findings:
- Issue: Resource handling — BufferedReader not closed; main throws IOException causing abrupt termination paths.
  Severity: Low
  Recommendation: Use try-with-resources for BufferedReader and handle IOException with a user-friendly message; avoid propagating checked exceptions from main in production samples.
  Compliance Impact: SOC2 / internal reliability controls (availability/operational resilience): minor.

- Issue: Console output includes unsanitized user-provided input (rowId) in error/success messages.
  Severity: Low
  Recommendation: Constrain/validate allowed characters for rowId at the command parsing layer (e.g., regex allowlist) and/or normalize before echoing. This prevents log forging/control characters in logs/terminal (e.g., CRLF, ANSI escapes) if this pattern is reused in server logs.
  Compliance Impact: SOC2 logging integrity expectations; internal secure logging guidelines.

- Issue: TableRow.radioGroupName() is hardcoded; may conflict when embedding multiple tables/components.
  Severity: Medium
  Recommendation: Make group name injectable/configurable (e.g., SelectionModel constructed with a groupName, or TableRow removed from owning UI naming). In UI contexts, radio buttons must share a group name per table instance but not across tables.
  Compliance Impact: Internal UI engineering standards; accessibility consistency.

- Issue: SelectionListener callback uses nullable parameter to represent "cleared" state.
  Severity: Low
  Recommendation: Prefer Optional<String> in callback or provide two callbacks (onSelected/onCleared) to avoid null handling bugs when integrated into larger systems.
  Compliance Impact: Internal code quality standards; reduces defect risk.

- Issue: ValidationException extends RuntimeException and is used for user input validation; IllegalArgumentException used elsewhere.
  Severity: Low
  Recommendation: Standardize exception strategy: either use IllegalArgumentException consistently for validation or keep ValidationException but document it and potentially make it unchecked with clear naming (already) while ensuring callers handle it.
  Compliance Impact: Internal maintainability standards.

- Issue: Potential performance/scalability concern — SelectionModel.findRow() is linear search.
  Severity: Low
  Recommendation: If row counts can be large in real UI usage, store a Map<String, TableRow> index for O(1) lookup; keep List for rendering order.
  Compliance Impact: SOC2 availability/performance considerations (minor).
