User Story ID: 104470
Review Summary: Overall code quality is good and generally aligns with Spring/JdbcTemplate best practices. Key gaps are around access control robustness (restore endpoint pre-auth too weak), input validation (versionNumber), sensitive detail leakage in audit logs, and architecture/packaging (multiple layers in one file, embedded DDL constant). No obvious injection flaws in SQL usage (parameterized queries used), and no resource leaks observed.

Findings:
Issue: Restore endpoint authorization is too permissive at controller layer (@PreAuthorize("isAuthenticated()")) and relies on service-side role checks
Severity: High
Recommendation: Enforce authorization at method boundary with strong declarative security, e.g., @PreAuthorize("hasAnyRole('ADMIN','TOOL_ADMIN','PROJECT_ADMIN')") on restore endpoint/service method, and keep canRestoreApp as defense-in-depth (or replace with centralized authorization service). Ensure 401 vs 403 behavior is consistent with security config.
Compliance Impact: SOC2 (access control enforcement). Potential internal policy violation if privileged action is not guarded at entry point.

Issue: Audit log messages include exception messages (dae.getMessage()) and potentially sensitive operational details
Severity: High
Recommendation: Avoid storing raw exception messages in audit trails; log a sanitized reason code and correlation ID. Keep detailed stack traces only in secured application logs with proper access controls. Consider structured audit schema (action, subject, actor, outcome, errorCode, requestId).
Compliance Impact: SOC2 (audit log integrity and minimization), potential privacy/internal policy issues if DB errors include sensitive data.

Issue: Missing input validation for versionNumber (e.g., negative/zero values) and appId (null not possible for path, but format validation via UUID conversion errors not handled explicitly)
Severity: Medium
Recommendation: Validate constraints explicitly: versionNumber >= 1; return 400 with clear message. Consider Bean Validation annotations (@Min(1)) on controller args and @Validated on controller. Add exception handler for MethodArgumentTypeMismatchException to return sanitized 400 responses.
Compliance Impact: SOC2 (reliability/availability controls); reduces risk of unexpected behavior.

Issue: Tight coupling / layered architecture violation: controller, service, repository, DTOs, exceptions, and DDL all in a single class/file
Severity: Medium
Recommendation: Split into separate top-level classes by layer/package: controller (..controller), service (..service), repository (..repository), dto (..dto), exceptions (..exception). Move DDL to Flyway/Liquibase migrations (e.g., db/migration/Vxxx__app_versioning.sql) rather than a Java constant.
Compliance Impact: Internal engineering standards (maintainability), SOC2 change management (migration traceability).

Issue: Potential sensitive data exposure: restoring config_json and storing it in DB without any data classification; no encryption-at-rest note for sensitive configurations
Severity: Medium
Recommendation: If config_json can contain secrets (API keys, credentials), ensure secrets are stored in a secret manager and referenced, not embedded in JSON. Apply encryption-at-rest where mandated, and add redaction when returning/processing config.
Compliance Impact: SOC2 (confidentiality), possibly PCI-DSS if payment data/secrets are included in configurations.

Issue: Improper error handling detail boundary: log.error includes stack trace (good for internal logs) but API throws generic ServerException without a global handler shown; risk of default error responses exposing details if not configured
Severity: Medium
Recommendation: Ensure a centralized @ControllerAdvice maps exceptions to sanitized ApiResponse without stack traces or internal messages. Confirm Spring Boot error settings (server.error.include-message/stacktrace) are disabled in prod.
Compliance Impact: SOC2 (information leakage control).

Issue: canAccessApp() authorization placeholder grants access to any authenticated user; no app-level ACL/tenant isolation enforced
Severity: High
Recommendation: Implement proper authorization checks (ownership/membership/tenant) using app metadata (e.g., app.project_id) and enforce in queries or policy layer. Add tests to prevent cross-tenant access.
Compliance Impact: SOC2 (logical access controls), potential privacy breach.

Issue: Duplicate row mapping logic in repositories (AppRow and AppVersionRow mappers repeated)
Severity: Low
Recommendation: Extract RowMapper constants or use BeanPropertyRowMapper (with care) / dedicated mapper methods to reduce duplication.
Compliance Impact: None direct; maintainability.

Issue: Magic strings for audit actions ("APP_VERSION_RESTORE", "APP_VERSION_RESTORE_FAILED")
Severity: Low
Recommendation: Use enum/constants for audit action names to ensure consistency and prevent typos.
Compliance Impact: SOC2 (audit consistency) minor.

Issue: Missing Javadoc on public API methods/classes (controller endpoints are public) beyond high-level comment
Severity: Low
Recommendation: Add Javadoc to controller/service public methods documenting parameters, authorization expectations, and error cases. Keep OpenAPI annotations as complementary.
Compliance Impact: Internal standards.
