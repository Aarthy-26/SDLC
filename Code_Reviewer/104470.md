User Story ID: 104470
Review Summary: Overall code quality is good for a single-file simulation and generally follows secure patterns (no DB/exec/deserialization). However, there are High-severity enterprise/security/compliance concerns: hardcoded authentication tokens (secrets), use of System.out for audit logging, potential sensitive error detail exposure, and lack of transport/security controls typical for SOC2/enterprise environments. Maintainability is acceptable but would benefit from layering (controller/service/repository), stronger input validation, and structured logging.

Findings:
Issue: Hardcoded authentication tokens (credential-like secrets) in source code via tokenToUser Map.of("builder-token", ...)
Severity: High
Recommendation: Remove hardcoded tokens. Integrate with an external identity provider (OIDC/JWT validation) or at minimum load tokens/keys from environment/secret manager (Vault/AWS Secrets Manager/KMS). Rotate any exposed tokens immediately. Add unit/integration tests using mocked auth.
Compliance Impact: SOC2/Internal policy risk (secret management). Potential PCI-DSS impact if similar practice used for production secrets. This violates common secure SDLC policies for credential storage.

Issue: Audit logging and operational logging uses System.out.println (stdout) and contains user/app identifiers
Severity: Medium
Recommendation: Use an approved logging framework (SLF4J + Logback/Log4j2) with JSON/structured logs, log levels, correlation IDs, and appenders to centralized logging. Ensure audit events are tamper-evident (write-once storage) and include requestId, source IP, and outcome.
Compliance Impact: SOC2 audit logging requirements may be only partially met; stdout is typically not sufficient for integrity/retention controls.

Issue: Potential information disclosure via error responses returning exception class and message (INTERNAL_ERROR) and restore failure "details"
Severity: High
Recommendation: Do not expose internal exception types/messages to clients. Return a generic error message and an opaque errorId; log the full exception server-side. Replace Map.of("exception", ... , "message", ...) with a safe, non-sensitive payload.
Compliance Impact: SOC2 (security principle) and internal security policies—exposing internal details increases exploitability.

Issue: Input validation gaps for path parameters (appId) and insufficient constraints on versionNumber
Severity: Medium
Recommendation: Validate appId against an allowlist pattern (e.g., ^[a-zA-Z0-9_-]{1,64}$) and enforce versionNumber bounds (e.g., >0 and reasonable max). Reject overly long inputs early. Add consistent 400 responses for validation failures.
Compliance Impact: SOC2 (input validation/hardening). Reduces risk of log injection and unexpected behavior.

Issue: Log injection risk in audit() by concatenating unsanitized values (appId, username, failureReason)
Severity: Medium
Recommendation: Use structured logging with field encoding. If remaining with string logs, sanitize/escape control characters (\r, \n, \t) and delimiters. Avoid logging raw exception messages; map to controlled failure codes.
Compliance Impact: SOC2 logging integrity. Helps prevent misleading audit trails.

Issue: Nested try/catch with broad catch (catch Exception restoreFailure) may swallow root cause classification
Severity: Medium
Recommendation: Catch more specific exceptions (e.g., RuntimeException only for simulated failures, or custom RestoreException). Preserve cause in server logs while returning generic client message. Consider separating restore into a service method returning a result object.
Compliance Impact: Internal reliability controls; improves incident response and auditability.

Issue: Concurrency/consistency: App.versionsByNumber is a plain HashMap inside App stored in ConcurrentHashMap; per-app lock protects restore but GET reads without lock
Severity: Medium
Recommendation: Either: (1) make versionsByNumber a ConcurrentHashMap, or (2) synchronize on per-app lock for reads that require consistency, or (3) make App immutable snapshots for reads. Current approach is mostly safe given seeding-only, but not robust for future writes.
Compliance Impact: SOC2 availability/reliability considerations.

Issue: Class/package structure not aligned to layered enterprise convention; single file with multiple responsibilities (HTTP routing, auth, domain model, storage, JSON serialization)
Severity: Medium
Recommendation: Split into packages/layers: controller (handler), service (version operations), repository (storage), dto (response models), security (auth). Introduce interfaces for testability. Keep JSON via a standard library (Jackson) with proper configuration.
Compliance Impact: Internal engineering standards; improves maintainability and reduces change risk.

Issue: Custom JSON serializer (toJson/escapeJson) is minimal and may fail edge cases (Map key ordering, unsupported types, encoding nuances)
Severity: Low
Recommendation: Use a vetted JSON library (Jackson) to avoid serialization bugs and injection issues. If custom remains, add tests for edge cases and ensure deterministic output if required.
Compliance Impact: Low; potential reliability issue.

Issue: Missing Javadoc on public API surface (main class and key methods); comments exist but not standard Javadoc for public methods
Severity: Low
Recommendation: Add Javadoc for public class/methods and key behaviors (auth model, error schema, concurrency guarantees). Generate API documentation if needed.
Compliance Impact: Internal standards.

Issue: Magic strings for permissions and endpoints ("READ_VERSIONS", "RESTORE_VERSIONS", path segments)
Severity: Low
Recommendation: Extract constants/enums for permissions and route segments; consider centralized router.
Compliance Impact: Internal standards; reduces defects.
