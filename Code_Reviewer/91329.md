User Story ID: 91329

Review Summary: Overall strong MVP architecture (Spring Boot, validation annotations, RFC6902 JSON Patch, atomic write + backup, constant-time API key comparison, and safe exception mapping). However, there are several high/medium-risk security and compliance gaps typical for local HTTP services: missing TLS and rate limiting, insufficient path traversal protection and file-access scoping, lack of request-size limits, and missing structured audit logging. Minor maintainability issues exist (unused variables, regex compilation strategy, and a few style/robustness improvements).

Findings:
- Issue: Inadequate path traversal / arbitrary file access control in validatedPath()
  Severity: High
  Recommendation: Restrict appPath/outputZip/backupDir to an allowlisted base directory (e.g., configured workspace root). Resolve toRealPath() and ensure the resolved path startsWith(baseDir). Reject absolute paths and enforce allowed filename patterns (e.g., app.json). Also apply the same validation to backupDir and outputZipStr.
  Compliance Impact: SOC2 (CC6/CC7) access control & change management risk; internal secure coding policies (file system access control). Potential data exposure if service can read/overwrite arbitrary files.

- Issue: No transport security (HTTP only) and weak authentication model for anything beyond localhost
  Severity: High
  Recommendation: Bind server to localhost only by default (server.address=127.0.0.1). If remote use is expected, require TLS (Spring Boot SSL) and stronger auth (mTLS or OAuth2). Explicitly document threat model and deployment constraints.
  Compliance Impact: SOC2 (CC6.1) network security; PCI-DSS (if any CHD traverses service) requires strong cryptography in transit.

- Issue: Missing rate limiting / brute force protection on API key filter
  Severity: Medium
  Recommendation: Add rate limiting (Bucket4j / Spring Cloud Gateway / servlet filter) and optionally incremental backoff on failed auth. Consider returning 429 for excessive requests.
  Compliance Impact: SOC2 (CC7.2) protects against abuse; internal resiliency standards.

- Issue: Potential sensitive data exposure via /package and file paths returned to clients
  Severity: Medium
  Recommendation: Avoid returning absolute filesystem paths (bundlePath, backupPath, appPath) to clients; return relative identifiers or mask base directories. Provide an option to disable path echoing.
  Compliance Impact: SOC2 confidentiality principle; internal data classification policy (exposing system structure).

- Issue: Request body for /package uses raw Map<String,Object> without validation
  Severity: Medium
  Recommendation: Replace with a typed DTO with @Valid constraints (e.g., @NotBlank optional fields, length limits). Enforce max path length and safe patterns.
  Compliance Impact: SOC2 input validation expectations; internal API governance.

- Issue: No explicit maximum request size / JSON depth limits (DoS risk)
  Severity: Medium
  Recommendation: Configure Spring/Tomcat max post size, max swallow size, and Jackson constraints (stream read constraints for depth/size) to mitigate large payloads. Also consider limiting patch operation count.
  Compliance Impact: SOC2 availability controls (CC7); internal non-functional requirements.

- Issue: RegexUtil recompiles patterns each call; potential ReDoS if patterns become complex
  Severity: Low
  Recommendation: Precompile Patterns as static final constants for known patterns used in interpretRequirementToPatch(). Keep patterns linear-time and bounded; set explicit length limits on requirementText.
  Compliance Impact: SOC2 availability; secure coding best practice.

- Issue: validatedPath() check for ".." is ineffective after normalize(); absolute paths not blocked
  Severity: High
  Recommendation: Remove the "contains('..')" check and replace with canonical resolution + baseDir enforcement. Explicitly reject path.isAbsolute(). Validate file extension and expected filename. Use Path#normalize + Path#toRealPath (NOFOLLOW_LINKS) when appropriate.
  Compliance Impact: SOC2 CC6/CC7; internal secure file handling policy.

- Issue: backupDir and outputZipStr are not validated; could write to sensitive locations
  Severity: High
  Recommendation: Apply same base-dir scoping and allowed path checks. Prefer server-controlled directories for backups and bundles, and accept only relative names from clients.
  Compliance Impact: SOC2 access control; change management; potential integrity breach.

- Issue: Zip creation without explicit file permission hardening and without ZIP Slip concerns addressed (future-proofing)
  Severity: Low
  Recommendation: Currently safe because entries are constant ("app.json", "manifest.json"). Keep it that way; if ever adding arbitrary files, validate entry names to prevent ZIP Slip.
  Compliance Impact: Secure coding best practice.

- Issue: GlobalExceptionHandler does not log exceptions; missing audit trail
  Severity: Medium
  Recommendation: Add structured server-side logging (with correlation IDs) for auth failures, validation failures, and unexpected errors. Ensure logs avoid storing API keys or full request bodies.
  Compliance Impact: SOC2 (CC7.2 logging/monitoring); internal audit logging policy.

- Issue: ApiKeyFilter uses System.getenv() on each request (perf + testability)
  Severity: Low
  Recommendation: Read expected key once at startup via @Value or ConfigurationProperties and refresh only if needed. Add unit tests for filter behavior.
  Compliance Impact: Internal engineering standards.

- Issue: Minor maintainability issues (dead code / unused variable)
  Severity: Low
  Recommendation: In generatePlan(), remove unused patchWrapper. Add unit tests for normalize/validate and patch generation. Consider splitting AppEnhancementService into smaller components (PlanGenerator, PatchApplier, Packager).
  Compliance Impact: None direct; improves maintainability (SOC2 change management indirectly).

- Issue: Lack of explicit CORS policy and CSRF considerations
  Severity: Low
  Recommendation: If called only by a local plugin (not a browser), disable CORS or keep restrictive defaults. If browser-based calls are possible, configure CORS allowlist and consider CSRF depending on auth mechanism.
  Compliance Impact: SOC2 (CC6) depending on exposure.
