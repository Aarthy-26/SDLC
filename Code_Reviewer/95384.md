User Story ID: 95384

Review Summary:
Overall the solution is clean, idiomatic Spring Boot (Java 17) with good separation of concerns, basic request validation, structured error handling, and useful latency instrumentation (Micrometer Timers) plus a simple TTL cache to reduce repeated reads. Maintainability is generally strong (records for DTOs, small classes, clear naming). Key improvement areas are: (1) better input validation for path variables (currently relies on manual checks only), (2) cache correctness/robustness for null loader results and potential memory growth, (3) more enterprise-grade caching and pagination semantics, (4) observability details (tags, percentiles), and (5) compliance hardening (error message hygiene, logging/audit, dependency governance, actuator exposure).

Findings:
- Issue: Path variable `id` is not bean-validated (only manually checked) and missing `@Min(1)` style constraint enforcement at controller boundary
  Severity: Medium
  Recommendation: Add `@Min(1)` to `@PathVariable long id` and keep the service guard as defense-in-depth. Example: `public ProjectDetailsDto getProjectDetails(@PathVariable("id") @Min(1) long id)`.
  Compliance Impact: SOC2—Input validation control expectations; reduces risk of unexpected error paths.

- Issue: Global exception handler returns `ex.getMessage()` directly for 400/404, potentially leaking internal details as the code evolves
  Severity: Medium
  Recommendation: Return a safer, user-friendly message (or a structured list of validation errors) and log the detailed message server-side with correlation id. For `NotFoundException`, avoid embedding identifiers if policy requires. Consider mapping validation exceptions into consistent field-error format.
  Compliance Impact: SOC2—Information disclosure; Internal policies around error-message hygiene.

- Issue: `GlobalExceptionHandler.handleServerError` does not log the exception
  Severity: Medium
  Recommendation: Log the exception at ERROR with a request correlation id (MDC) while still returning a generic message. Add rate limiting if needed. Ensure logs exclude sensitive data.
  Compliance Impact: SOC2—Auditability/incident response (logging and monitoring requirements).

- Issue: TTL cache does not handle `loader.get()` returning null; null will cause NPE when returning `updated.value()`
  Severity: Medium
  Recommendation: Enforce non-null cache values (document and check) or allow Optional values. Example: `V loaded = Objects.requireNonNull(loader.get(), "loader returned null");`.
  Compliance Impact: Reliability/availability (SOC2 availability). Not directly PCI.

- Issue: TTL cache can grow unbounded for `projectDetailsCache` (keyed by project id) if many unique ids are requested; no max size/eviction
  Severity: Medium
  Recommendation: Add size bounds + eviction policy or adopt a proven cache (Caffeine) with `maximumSize`, `expireAfterWrite`, and stats. If avoiding deps, implement periodic cleanup and a max entries cap.
  Compliance Impact: SOC2 availability (resource exhaustion/DoS risk).

- Issue: Cache stampede prevention is per-key, but clock is read twice (outside and inside `compute`); minor inconsistency and extra calls
  Severity: Low
  Recommendation: Remove the pre-check `map.get` branch or reuse a single time source within compute. Keep it simple: just `map.compute`.
  Compliance Impact: None.

- Issue: Caching of `/api/apps` ignores pagination in the cache key (caches full list, then sublists)
  Severity: Low
  Recommendation: This is acceptable for small lists but may be inefficient for large datasets. Consider caching per page/size key, or better: push pagination to the repository/database layer and cache page results (or avoid caching huge lists).
  Compliance Impact: SOC2 performance/availability; internal performance standards.

- Issue: `Math.multiplyExact(page, size)` can throw `ArithmeticException` for extreme integers; although constrained, controller constraints are present but defense could be more graceful
  Severity: Low
  Recommendation: Since `page` is unbounded in validation, a huge page could overflow. Add `@Max` on `page` (or clamp) and/or handle `ArithmeticException` as 400 with a safe message.
  Compliance Impact: SOC2 availability (avoid unexpected 500).

- Issue: Actuator exposure includes `metrics` and `prometheus` without any mention of network restrictions
  Severity: Medium
  Recommendation: In enterprise deployments, restrict actuator endpoints to internal networks, require auth, or run on a separate management port. Ensure Prometheus scraping is secured.
  Compliance Impact: SOC2 security; potential information leakage. If later handling card data, PCI-DSS requires strict segmentation and access control.

- Issue: Micrometer timers lack useful tags (endpoint, outcome) and no histogram/percentiles configuration
  Severity: Low
  Recommendation: Add tags (e.g., `endpoint=apps`, `method=GET`) and consider enabling percentiles/histograms via configuration (`management.metrics.distribution.*`). Consider using `@Timed` with tags for standardization.
  Compliance Impact: SOC2 monitoring controls.

- Issue: In-memory repositories are fine for sample but not production-safe; concurrency semantics are inconsistent (synchronized map but unsynchronized `get` access)
  Severity: Low
  Recommendation: For sample OK. For real: use proper persistence layer or `ConcurrentHashMap` without external synchronization blocks. If keeping synchronization, wrap all access consistently.
  Compliance Impact: Reliability; no direct regulatory mapping.

- Issue: Missing OpenAPI/contract documentation and standard response envelopes for pagination (no total count, next page)
  Severity: Low
  Recommendation: Consider returning a paged response DTO containing `items`, `page`, `size`, `total`. Add OpenAPI annotations for enterprise API governance.
  Compliance Impact: Internal API standards; SOC2 change management (clear contracts).
