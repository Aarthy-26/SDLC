User Story ID: 95384

Review Summary:
Overall quality is good (clear layering, caching, validation, structured error handling). Primary concerns are operational safety and enterprise compliance: unrestricted Prometheus endpoint exposure, unbounded/undeclared thread pool lifecycle (potential resource leak), and error-message leakage that could expose internal identifiers. Additional maintainability improvements include externalizing executor management, adding cache observability, and standardizing exception handling for validation and timeouts.

Findings:
- Issue: Prometheus/actuator endpoint configured as unrestricted access (management.endpoint.prometheus.access=unrestricted)
  Severity: High
  Recommendation: Restrict actuator endpoints to authenticated/authorized access and/or bind management server to internal network. Prefer Spring Security with role-based access, IP allowlists, and separate management port (management.server.port). Review exposure list; do not expose prometheus publicly.
  Compliance Impact: SOC2 (security principle), internal security policies; may violate PCI-DSS requirement to restrict access to system components and monitoring data if deployed in PCI scope.

- Issue: Custom ExecutorService created in ProjectDetailsService without lifecycle management (no shutdown) and created per service instance
  Severity: High
  Recommendation: Define a managed Executor bean (e.g., ThreadPoolTaskExecutor) with proper shutdown on context close, bounded queue, and rejection policy. Avoid creating raw executors in service constructors. Add @PreDestroy to shutdown if keeping ExecutorService.
  Compliance Impact: SOC2 availability/reliability controls; operational risk and potential DoS via resource exhaustion.

- Issue: Potential thread exhaustion / request amplification due to per-request async submission + blocking get()
  Severity: Medium
  Recommendation: Prefer non-blocking HTTP clients (WebClient) with proper timeouts for real downstream calls. If keeping executor, ensure pool sizing, queue bounds, and circuit breaking (Resilience4j) to prevent load spikes. Consider bulkhead + timeout + fallback response.
  Compliance Impact: SOC2 availability; internal SLO/SLI policies.

- Issue: Timeout exception message includes projectId and is returned to client via ex.getMessage()
  Severity: Medium
  Recommendation: Do not return raw exception messages to clients. Return a generic message and log details server-side with correlation ID. For example: message="Downstream dependency timed out" and include projectId only in logs.
  Compliance Impact: SOC2 confidentiality; internal logging/data minimization policies. Not typically PCI data, but pattern is risky.

- Issue: Validation error handling may not trigger as intended for @PathVariable @Min(1); handler for MethodArgumentNotValidException is primarily for @RequestBody
  Severity: Medium
  Recommendation: For path variables, ConstraintViolationException is typical; enhance handler to provide meaningful violation details (without sensitive data). Add tests for /api/projects/0/details and /api/projects/-1/details.
  Compliance Impact: Internal API standards; security input validation best practices.

- Issue: Correlation ID accepted from client with minimal validation; length check only, no character whitelist
  Severity: Low
  Recommendation: Enforce an allowlist regex (e.g., [A-Za-z0-9-]{1,64}) to reduce log injection risk. If invalid, generate new ID. Consider also normalizing header case and supporting W3C traceparent.
  Compliance Impact: SOC2 logging integrity; internal secure logging requirements.

- Issue: Cache configuration lacks metrics/monitoring and does not specify recordStats
  Severity: Low
  Recommendation: Enable Caffeine stats (recordStats) and export via Micrometer for hit rate/evictions. Consider per-cache configuration and documenting TTL rationale.
  Compliance Impact: SOC2 monitoring controls; internal observability standards.

- Issue: Cache key strategy: apps cache uses constant key 'all' which is fine now but can become problematic if endpoint evolves (e.g., user-specific data)
  Severity: Low
  Recommendation: Document assumption that response is not user-specific. If auth context is later added, include tenant/user in cache key or disable caching for personalized responses.
  Compliance Impact: SOC2 confidentiality; potential data leakage across tenants/users if requirements change.

- Issue: Simulated downstream delay uses Thread.sleep based on projectId modulo 2001; in real code, timeouts should be enforced at client level (connect/read)
  Severity: Low
  Recommendation: When integrating real downstream calls, use client-side timeouts (e.g., RestClient/WebClient timeouts) and consider retries with backoff and jitter.
  Compliance Impact: Internal resilience standards.
