User Story ID: 95384

Review Summary:
Overall, the codebase demonstrates solid enterprise-grade practices for a performance-focused Spring Boot 3 / Java 17 service: pagination is implemented, sorting is allowlisted, caching is bounded with TTL, N+1 query risk is mitigated via `@EntityGraph`, validation is present, Open-Session-In-View is disabled, and errors are returned in a consistent JSON model with correlation IDs.

Primary risks/concerns are centered around: (1) cache key composition and cache correctness under filtering, (2) potentially misleading pagination totals when applying in-memory filtering, (3) missing cache invalidation strategy and caching of potentially sensitive fields, (4) insufficient logging safeguards (possible user-controlled correlation id / path values), and (5) compliance hardening gaps (security headers, authn/authz assumptions, audit logging completeness).

Findings:

- Issue: In-memory filtering combined with database pagination can produce incorrect results and misleading totals
  Severity: Medium
  Recommendation: When both `ownerFilter` and `nameFilter` are provided, do not apply one filter in-memory after paging. Instead:
  - Implement a single DB query that applies both filters (e.g., `findByOwnerContainingIgnoreCaseAndNameContainingIgnoreCase(...)`) or use `JpaSpecificationExecutor` / QueryDSL.
  - Ensure `totalElements` reflects the fully filtered dataset.
  Compliance Impact: SOC2 (Availability/Integrity) — incorrect pagination metadata can affect downstream reporting and correctness.

- Issue: Cache key uses `#sort` object stringification; may be unstable and can lead to low cache hit ratio / unintended key variation
  Severity: Medium
  Recommendation: Build cache keys from normalized primitives:
  - Normalize sort into canonical form like `property:dir` (e.g., `name:ASC`).
  - Trim/normalize filters (`ownerFilter`, `nameFilter`) before key creation.
  - Consider using a dedicated key object with stable `equals/hashCode` rather than string formatting.
  Compliance Impact: SOC2 (Availability/Performance) — unstable keys reduce cache effectiveness and can increase load.

- Issue: Potential cache poisoning / cache fragmentation via unbounded filter values
  Severity: Medium
  Recommendation: Add validation constraints to request parameters `owner` and `name`:
  - Limit length (e.g., 1..100) and pattern (e.g., `^[\\p{L}\\p{N} _.-]{0,100}$`), as appropriate.
  - Normalize whitespace.
  - Consider disabling caching when free-text filters are present, or enforce a limited set of filterable fields.
  Compliance Impact: SOC2 (Availability) — attacker can generate many unique cache keys, evicting useful entries (cache DoS).

- Issue: Caching of project details may serve stale data; no explicit invalidation strategy
  Severity: Medium
  Recommendation: Define a cache eviction policy aligned to data update patterns:
  - Add `@CacheEvict` on write operations (if/when they exist) for apps/projects.
  - Use shorter TTL for highly dynamic data or consider cache versioning.
  - Document cache consistency expectations (read-your-writes vs eventual consistency).
  Compliance Impact: SOC2 (Integrity) — stale data may violate accuracy expectations.

- Issue: Correlation ID accepts arbitrary header value and returns it to clients; potential header injection concerns and log forging
  Severity: Medium
  Recommendation: Sanitize/validate `X-Correlation-Id`:
  - Enforce a max length (e.g., 64) and strict character allowlist (e.g., `[A-Za-z0-9-]{1,64}`).
  - Reject/replace values containing control characters.
  - Consider generating server-side IDs always, and optionally store client-provided id separately.
  Compliance Impact: SOC2 (Security/Logging) — untrusted input in logs can impair audit trail integrity.

- Issue: Request logging is inconsistent and could expose identifiers; lacks structured logging and does not record correlationId explicitly in message
  Severity: Low
  Recommendation: Prefer structured logging fields and avoid logging sensitive identifiers unless necessary:
  - Log `correlationId` (already in MDC pattern) and route template rather than raw URL.
  - Consider using `HandlerInterceptor` or `OncePerRequestFilter` for consistent latency logging across endpoints.
  Compliance Impact: SOC2 (Audit/Monitoring) — consistency improves incident investigation; avoid sensitive data exposure.

- Issue: Global exception handler swallows server errors without logging the exception
  Severity: Medium
  Recommendation: Log exception details server-side (with correlationId) while returning a generic message to clients:
  - In `serverError`, add `log.error("Unhandled exception", ex);`
  - Ensure logs do not include secrets/PII.
  Compliance Impact: SOC2 (Monitoring/Incident Response) — without server-side error logs, triage and forensic analysis are hindered.

- Issue: Error messages may reflect internal validation messages and could leak implementation details
  Severity: Low
  Recommendation: Standardize client-facing validation messages:
  - Map constraint violations to a controlled message format.
  - Optionally include an error code catalog.
  Compliance Impact: SOC2 (Security) — minimize information disclosure.

- Issue: Missing security headers and baseline hardening configuration
  Severity: Medium
  Recommendation: Add common HTTP security headers (ideally via Spring Security even if auth is upstream):
  - `X-Content-Type-Options: nosniff`, `X-Frame-Options`, `Content-Security-Policy` (as applicable), `Referrer-Policy`, `Cache-Control` for sensitive endpoints.
  - Disable H2 console in non-dev profiles.
  Compliance Impact: SOC2 (Security) — baseline hardening expectation; PCI-DSS if system is in scope.

- Issue: H2 console enabled by default
  Severity: High (if deployed beyond local/dev)
  Recommendation: Ensure `spring.h2.console.enabled` is profile-scoped:
  - Default false; enable only in `application-dev.properties`.
  - Restrict access with authentication if ever enabled.
  Compliance Impact: SOC2 + PCI-DSS — administrative consoles in production are a common compliance violation.

- Issue: `spring.jpa.hibernate.ddl-auto=create` risks destructive schema recreation
  Severity: High (if used outside dev/test)
  Recommendation: Scope DDL-auto to dev/test only:
  - Use Flyway/Liquibase for controlled migrations.
  - Set `validate` or `none` in production.
  Compliance Impact: SOC2 (Change management, Availability/Integrity) — uncontrolled schema changes and data loss risk.

- Issue: DataSeeder runs automatically and writes synthetic data; risk in non-dev environments
  Severity: High (if included in production build)
  Recommendation: Guard seeding with profile:
  - Annotate with `@Profile("dev")` or condition on property.
  - Ensure no test data is created in production.
  Compliance Impact: SOC2 (Integrity) — unintended data creation; PCI-DSS if datasets overlap with regulated data.

- Issue: Many-to-many association fetch via EntityGraph may still return large payloads; no limits on associated apps
  Severity: Medium
  Recommendation: Consider:
  - Adding pagination/limits or a summarized endpoint variant.
  - Using DTO projection queries to fetch only required columns.
  Compliance Impact: SOC2 (Availability/Performance) — large payloads can degrade service and increase cost.

- Issue: Caching `/api/apps` page results can amplify memory usage and cache churn; maximumSize 10,000 might be high without sizing analysis
  Severity: Low/Medium
  Recommendation: Tune caching based on traffic patterns:
  - Reduce maximum size or use `maximumWeight` with a weigher.
  - Consider caching only the most common pages (e.g., first page) or only unfiltered requests.
  Compliance Impact: SOC2 (Availability) — memory pressure can cause instability.

- Issue: Missing explicit API versioning and contract documentation (OpenAPI)
  Severity: Low
  Recommendation: Add OpenAPI/Swagger annotations or springdoc-openapi for enterprise API governance.
  Compliance Impact: Internal policy / SOC2 (Change management) — improves traceability and controlled changes.
