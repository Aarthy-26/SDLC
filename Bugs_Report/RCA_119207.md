## 1. Executive Summary
The bug describes BIM generation taking excessive time and eventually failing, which blocks the following workflow steps. In the repository, the clearest relevant code pattern is synchronous external API execution in `APIExecutionService` invoked through `AppsAPIService`, while a separate async job framework exists for long-running work. That mismatch makes long-running IMS conversion requests a likely source of timeout/failure behavior, but the ADO item lacks description, repro steps, logs, comments, attachments, and linked fix artifacts needed to prove that this exact path caused the incident. The recommended fix is to move BIM generation onto the existing async execution path and expose job-based completion instead of holding the request open.

## 2. Impact
The failure blocks BIM generation and any downstream step that depends on the generated output, which matches the ticket title. The work item is tagged `UAT- Not Leakage`, so the observed impact is at least in UAT. Frequency and exact blast radius are not stated in the work item.

## 3. Root Cause
The single most likely cause is that BIM generation is executed as a synchronous external/API-driven operation even though the codebase already contains dedicated async orchestration for long-running jobs. Evidence: `com.ascendion.datapowerAI.service.implementation.AppsAPIService#execute` dispatches `ExecutionMode.SYNC` to `APIExecutionService#executeSynchronously`, while `com.ascendion.datapowerAI.service.APIExecutionService` is still bound by request/response lifecycle and configured timeouts from `RestTemplateConfig` (10s connect, 30s response) and the external call path can fail before downstream processing completes. The missing evidence is the actual IMS endpoint, call chain, runtime logs, stack trace, or linked commit/PR proving BIM generation is mapped to this service path; without that, the cause cannot be confirmed or ruled out conclusively.

## 4. Contributing Factors
The work item is closed, but the ADO payload returned only title, assignee, state, area, iteration, and tags; it did not include comments, discussion, linked commits/PRs, or attachments that could identify the actual shipped fix. The repository contains async infrastructure (`AsyncJobService`, `AsyncOrchestratorService`, `ExternalAsyncPollingService`) separate from the sync path, which increases the risk that a long-running conversion flow remains on the wrong execution mode. Timeout-oriented configuration in `RestTemplateConfig` further increases the chance that a long BIM generation request fails before completion.

## 5. Fix
- **Immediate:** Configure the BIM generation integration to use `ExecutionMode.EXTERNAL_ASYNC` or `ExecutionMode.INTERNAL_ASYNC` in `com.ascendion.datapowerAI.entity.GenericAPI` and invoke it through `AppsAPIService#execute` so the request is submitted as a job instead of being held open synchronously.
- **Permanent:** Ensure the IMS convert flow is explicitly modeled as async using `AsyncApiConfig`, `AsyncOrchestratorService`, and `ExternalAsyncPollingService`, with persisted status/result handling in `AsyncJob`; this removes request-timeout coupling and lets subsequent steps depend on job completion state rather than a single HTTP round trip.

## 6. Prevention
Add an integration test that simulates a long-running BIM/external conversion response and verifies the flow submits and tracks an async job instead of timing out synchronously. Add logs/metrics around job submission, external execution ID extraction, poll attempts, terminal status, and timeout/failure counts. Add an alert for repeated async job failures or poll exhaustion in IMS-tagged APIs.
