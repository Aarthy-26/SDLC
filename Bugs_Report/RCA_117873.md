## 1. Executive Summary
The paginator page-size selector was reported as not working on the Convert, Test, and Validate screens. In the Test screen code, the table is rebound on every `activeRuns$` polling emission via `this.dataSource.data = [...this.dataSource.data]`, which can interfere with Angular Material paginator state and make page navigation and page-size changes appear ineffective while background polling is active. The Analyze screen already contains an inline fix comment describing this same failure mode and limits rebinding to actual execution-state changes, which is strong evidence that the same class of issue affected the other tabular screens. The recommended fix is to stop rebinding the data source on every poll tick and only reassign when row state actually changes, then apply the same guard consistently to Convert, Test, and Validate components.

## 2. Impact
Users on the DMS Azure UI are affected when working with grid-heavy screens that rely on Angular Material pagination, specifically Convert, Test, and Validate. When multiple rows exist and background execution polling is active, changing items per page can appear broken because the table keeps re-rendering and the paginator state is disrupted. This impacts review and monitoring workflows on those screens and reduces usability for larger result sets. Ticket evidence did not include repro video, comments, attachments, or environment details beyond the Azure DMS area, so impact frequency cannot be confirmed from the work item alone.

## 3. Root Cause
**Confidence: Probable.** In `src/app/components/domain-data-test-build/domain-data-test-build.component.ts`, the `activeRuns$` subscription in `ngOnInit()` updates each row and then unconditionally executes `this.dataSource.data = [...this.dataSource.data];`. This forces a table re-render on every monitoring poll even when no row state changed, which is a known way to disrupt Angular Material paginator interaction. Supporting evidence exists in `src/app/components/domain-data-table-analyze/domain-data-table-analyze.component.ts`, where the same pattern is explicitly called out in comments as the cause of paginator issues and is fixed by rebinding only when `executionStateChanged` is true. The work item did not include comments, linked commits, PRs, repro assets, or stack traces, so confirmation would require either the actual linked code change for this ticket or a runtime reproduction on the Convert/Test/Validate tabs while polling is active.

## 4. Contributing Factors
The components mix table interaction state with live execution-monitoring updates, so a polling cycle can trigger unnecessary UI refreshes during user pagination actions. The Test component contains the problematic unconditional rebind, while the Analyze component already shows a corrected pattern, indicating the issue was likely introduced by inconsistent implementation across similar screens. The work item has no acceptance criteria or linked fix artifacts, which limits direct verification of the exact production patch.

## 5. Fix
- **Immediate:** In each affected screen component, compute whether any row execution state actually changed during the `activeRuns$` subscription and only then run `this.dataSource.data = [...this.dataSource.data];`. This preserves paginator state during polling and addresses the reported page-size selector behavior.
- **Permanent:** Extract the polling-to-table update logic into a shared helper or base pattern used by Convert, Test, Validate, and Analyze so all grid screens normalize statuses and gate data-source rebinding consistently. Also avoid any other unconditional data-source reassignment during passive polling unless the underlying row data truly changed.

## 6. Prevention
Add component tests that simulate multi-page datasets and active polling, then verify that changing paginator page size updates the rendered row count correctly. Add regression coverage for each of the Convert, Test, and Validate screens specifically, because the issue appears in repeated table implementations rather than a shared paginator wrapper. Lightweight UI telemetry or debug logging around paginator `pageIndex` and `pageSize` during polling would also make this class of regression easier to detect.
